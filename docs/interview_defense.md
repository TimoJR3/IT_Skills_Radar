# Interview Defense

## 60 секунд

`IT Skills Radar` — это portfolio data-project на подготовленных данных junior/intern data-product вакансий. Я сделал end-to-end pipeline: загрузка `JSON/CSV`, validation, cleaning, нормализация ролей и skills, хранение в PostgreSQL, SQL-витрины, FastAPI и Streamlit dashboard.

Аналитически проект отвечает на несколько вопросов: какие навыки чаще встречаются в вакансиях, чем отличаются роли, как меняется доля skills по месяцам и какие навыки дают зарплатный аналитический сигнал. Важно: я не делаю причинных выводов по зарплате, потому что вакансии и неполные salary data не доказывают, что навык сам повышает доход.

Проект показывает навыки, которые нужны Data/Product Analyst: подготовка данных, нормализация справочников, SQL aggregation, проектирование витрин, API для аналитических агрегатов, dashboard storytelling, тесты и воспроизводимый запуск через Docker.

## Какие вопросы могут задать

### Почему не notebook?

Notebook удобен для EDA, но я хотел показать маленький data product: данные проходят через ingestion, сохраняются в БД, считаются SQL views, отдаются через API и визуализируются в dashboard. Так результат можно переиспользовать и проверять.

### Почему PostgreSQL views, а не расчеты только в Python?

Views фиксируют аналитическую логику ближе к данным. Это упрощает проверку grain, фильтров и формул, а API и dashboard остаются тонкими слоями поверх готовых агрегатов.

### Что такое grain витрин?

Grain — минимальный уровень детализации строки. Например, `top_skills_by_role` имеет grain `role + seniority + skill`, а `skills_trend_monthly` — `month + role + seniority + skill`. Это важно, чтобы не смешивать метрики разных уровней.

### Как проверялась корректность?

Я добавил pytest для нормализации, API, helper-функций dashboard и SQL schema files. Для аналитики можно делать spot checks: вручную взять роль и навык, посчитать число вакансий в normalized tables и сравнить с SQL view.

### Что значит salary premium?

Это разница медианных зарплат вакансий с навыком и без навыка внутри сопоставимого среза `RUB/month`. Это correlation-style signal, а не причинный эффект.

### Почему нельзя делать причинные выводы по зарплате?

Потому что вакансии не являются экспериментом: роли, компании, регионы, seniority, формулировки и заполненность зарплат могут смешиваться. Навык может встречаться в более дорогих ролях, но это не доказывает, что именно он повышает зарплату.

### Какие ограничения данных?

Данные подготовлены локально и не являются полной репрезентативной выгрузкой рынка. Возможны смещения по источнику, периоду, региону, компаниям и текстам вакансий. Зарплаты указаны не всегда, а rule-based extraction skills может пропускать синонимы или неоднозначные формулировки.

### Как бы улучшил проект дальше?

Я бы добавил source metadata, расширил период сбора, сделал quality report по coverage, добавил confidence/минимальные пороги для salary signal и вынес нормализацию skills в версионируемый справочник с review-процессом.

## Какие SQL и аналитические навыки подтверждает проект

- Проектирование normalized schema: `roles`, `skills`, `vacancies`, `vacancy_skills`, `salary_info`.
- Many-to-many model для вакансий и навыков.
- SQL views как аналитический слой.
- `COUNT(DISTINCT ...)`, `GROUP BY`, `JOIN`, `FILTER`, `PERCENTILE_CONT`, `DATE_TRUNC`, window functions.
- Работа с grain витрин и предотвращение неверных агрегатов.
- Расчет долей: `vacancy_share`, `skill_penetration_in_role`, `role_share_of_skill`, `salary_coverage`.
- Аккуратная интерпретация salary metrics без причинных утверждений.
- Dashboard storytelling: от overview к деталям, трендам и ограничениям.
