# 09. Глоссарий

## Предметная область

| Термин | Определение | Где в системе |
|---|---|---|
| Вакансия | Одно объявление о работе из источника после нормализации | `vacancies` |
| Источник (source) | Откуда получена вакансия: `hh_ru`, `habr_career`, `superjob`, `manual` | `vacancies.source_name` |
| Бизнес-ключ вакансии | Пара `(source_name, source_vacancy_id)`, однозначно определяющая вакансию | UNIQUE в `vacancies` |
| Роль | Нормализованная профессия: `data_analyst`, `product_analyst`, `data_scientist`, `ml_engineer`, `other_data_role` | `roles.role_code` |
| Группа ролей | Укрупнённая категория роли: `data`, `analytics`, `product`, `ml` | `roles.role_group` |
| Грейд (seniority) | Уровень позиции: `intern`, `junior`, `middle`, `senior`, `lead`, `unknown` | `vacancies.seniority_level` |
| Entry-level | Грейды `intern` и `junior` | `analytics.junior_roles_overview` |
| Навык | Каноническая компетенция из словаря (10 навыков) | `skills` |
| Slug навыка | Стабильный машинный идентификатор навыка, например `python`, `a_b_testing` | `skills.skill_slug` |
| Синоним (алиас) навыка | Вариант написания, который приводится к каноническому навыку: `Postgres` → `postgresql` | `normalization.py` |
| Обязательный навык | Навык, отмеченный как требование вакансии | `vacancy_skills.is_required` |
| Зарплатная вилка | Границы `salary_from` – `salary_to` | `salary_info` |
| Середина вилки | Значение, по которому считаются медианы и средние | `salary_info.salary_mid` |
| Gross / Net | Зарплата до / после вычета налогов | `salary_info.gross_type` |
| Доля вакансий (vacancy_share) | Доля вакансий группы «роль + грейд», где встречается навык | `top_skills_by_role`, `skills_trend_monthly` |
| Ранг навыка (skill_rank) | Место навыка по числу вакансий внутри группы «роль + грейд» | `top_skills_by_role` |
| Проникновение навыка в роль | Доля вакансий роли, в которых встречается навык | `role_skill_distribution.skill_penetration_in_role` |
| Доля роли в спросе на навык | Какая часть всех вакансий с навыком приходится на роль | `role_skill_distribution.role_share_of_skill` |
| Покрытие зарплатой (salary_coverage) | Доля вакансий, в которых указана сопоставимая зарплата | `junior_roles_overview` |
| Зарплатный сигнал (премия) | Разница медиан зарплат вакансий с навыком и без него. Корреляция, а не причинность | `skill_salary_premium` |
| Активная вакансия | Вакансия, открытая на момент сбора; только такие попадают в витрины | `vacancies.is_active` |

## Данные и обработка

| Термин | Определение |
|---|---|
| Ingestion | Загрузка данных в систему: чтение, валидация, нормализация, запись |
| Dry-run | Режим загрузки без записи в БД для проверки файла (`--dry-run`) |
| Валидация | Проверка обязательных полей (`source_vacancy_id`, `title`, `company_name`) и типов |
| Очистка (cleaning) | Удаление HTML, схлопывание пробелов, пустые строки → `NULL` (`clean_text()`) |
| Нормализация | Приведение значений к справочникам: роль, грейд, навыки, валюта, период, формат работы |
| Rule-based | Подход на правилах (regex, словари) без машинного обучения |
| Raw-слой | Исходные данные без изменений с метаданными сбора (`raw_source_metadata`) |
| Final-слой | Нормализованные таблицы, готовые к аналитике |
| Витрина (data mart) | Представление с агрегатами под конкретный вопрос; в проекте — `VIEW` в схеме `analytics` |
| Зерно витрины | Что описывает одна строка витрины, например «роль + грейд + навык» |
| VIEW / MATERIALIZED VIEW | Сохранённый запрос, вычисляемый при каждом обращении / сохранённый результат, который нужно обновлять |
| Upsert | Вставка записи или обновление существующей по ключу (`INSERT … ON CONFLICT … DO UPDATE`) |
| Идемпотентность | Свойство операции давать тот же результат при повторном выполнении |
| Checksum | Хэш содержимого записи (SHA-256), позволяет понять, изменилась ли она |
| Parser version | Версия правил обработки, сейчас `rule_based_v1` |
| Data quality (DQ) | Набор проверок корректности и полноты данных |

## Интеграция и архитектура

| Термин | Определение |
|---|---|
| REST API | Стиль HTTP-API, где ресурсы адресуются URL и читаются методом `GET` |
| OpenAPI | Стандарт машиночитаемого описания REST API (файл `api/openapi.yaml`) |
| Problem Details (problem+json) | Стандартный формат ошибок HTTP API по RFC 9457: `type`, `title`, `status`, `detail`, `instance` |
| 400 / 404 / 422 / 500 / 503 | Некорректный запрос / не найдено / ошибка валидации параметров / внутренняя ошибка / сервис временно недоступен |
| Событие (event) | Сообщение о факте, который уже произошёл, например `vacancy.ingested` |
| Топик | Именованный поток сообщений в брокере (Kafka) |
| Партиция | Часть топика; порядок сообщений гарантируется внутри партиции |
| Offset | Позиция сообщения в партиции; фиксация offset означает «обработано» |
| Consumer group | Группа экземпляров потребителя, между которыми распределяются партиции |
| At-least-once | Гарантия, при которой сообщение будет доставлено минимум один раз, возможны повторы |
| DLQ (Dead Letter Queue) | Отдельный топик для сообщений, которые не удалось обработать |
| Backoff | Растущая пауза между повторными попытками |
| JSON Schema | Стандарт описания структуры JSON-документа для валидации |
| SLA | Согласованный уровень сервиса: свежесть, задержка, доступность |
| C4 | Модель архитектурных диаграмм: Context, Container, Component, Code |
| ADR | Architecture Decision Record — запись архитектурного решения с альтернативами и последствиями |
| Healthcheck | Проверка работоспособности сервиса (`GET /health`, healthcheck в Docker Compose) |
| Наблюдаемость | Возможность понять состояние системы по логам, метрикам и трассировкам |
| p95 | 95-й перцентиль: 95 % запросов выполняются не дольше этого времени |
| CI | Непрерывная интеграция: автоматическая сборка и тесты на каждый коммит (GitHub Actions) |

## Системный анализ

| Термин | Определение |
|---|---|
| Стейкхолдер | Лицо или группа, заинтересованные в системе или влияющие на неё |
| Scope (in / out) | Границы: что система делает и что сознательно не делает |
| User story | Требование в форме «Как <роль>, я хочу <действие>, чтобы <ценность>» |
| AC (acceptance criteria) | Критерии приёмки истории, в проекте — в формате Given / When / Then |
| Use case | Сценарий взаимодействия актора с системой: основной, альтернативные потоки, исключения |
| НФТ | Нефункциональные требования: производительность, надёжность, безопасность и т. д. |
| MoSCoW | Приоритизация: Must, Should, Could, Won't |
| BPMN | Нотация моделирования бизнес-процессов: события, задачи, шлюзы, дорожки |
| AS-IS / TO-BE | Текущее / целевое состояние процесса или системы |
| Swimlane (дорожка) | Часть диаграммы процесса, закреплённая за участником |
| Шлюз XOR | Точка ветвления, где выбирается ровно один путь |
| ER-диаграмма | Модель сущностей и связей базы данных |
| Словарь данных | Описание таблиц и полей: тип, обязательность, смысл, допустимые значения |
| Sequence-диаграмма | Диаграмма обмена сообщениями между участниками во времени |
| Трассировка требований | Связь цели → истории → сценария → данных → API → теста |
| Проектное решение | В этой документации: элемент целевого состояния, которого нет в текущем коде |
